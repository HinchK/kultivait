# Cost model duality: metered cash and notional value tracked as separate lenses

Once pay-per-token frontier providers land (docs/adr/0004-api-frontier-surface.md), a single "spent" number conflates two different things: cash actually billed by a metered API, and the priced value of a dispatch consumed under an already-paid subscription CLI. The ledger therefore records **two costs per dispatch**: `cost_usd` is redefined as **metered cash** (API real spend — OpenRouter's `usage.cost` or tokens × pinned price; CLI and local record $0 — subscription capacity is marginal-cost-free once paid), and a new additive `notional_usd` records the dispatch's **notional value** at the target's own pay-per-token prices (CLI dispatches: tokens × `CLI_PRICING`, exactly what `cost_usd` held before; API dispatches: equal to metered; local: $0). Migration is lossless: legacy entries default `notional_usd = cost_usd` (which was notional for CLI tiers) with metered $0, so history reinterprets cleanly with no rewrite. The harvest baseline stays **one declared reference price** for the whole season — default remains the flat $3/$15 per MTok frontier reference for cross-season comparability, overridable in config to an exact pinned model's prices — rather than per-dispatch counterfactuals that drift as the route menu changes. The harvest prints both lenses: baseline (season at reference prices), notional spent (value consumed across subscription + API), **cash out** (metered API only), and kept-in-pocket = baseline − notional, so cash never inflates savings and subscription value never hides the real bill. The tollbooth's route menu keeps its uniform notional estimate as every option's primary figure (preserving the price-ascending total order of docs/adr/0003-route-menu-and-frontier-targets.md and apples-to-apples comparison), with a cash annotation per kind: API options append `· metered cash ≈$Y`, CLI options `· subscription $0 cash`, keep-it-local stays $0.

## Considered Options

- **Notional-primary `cost_usd` with a cash sidecar**: rejected — every downstream consumer (harvest, escalations, the future benchmark) would keep reading a mixed number; the conflation the ticket exists to dissolve would survive as the primary field.
- **Per-entry exact counterfactual baseline** (each entry priced at its top-ranked frontier target's pinned price): rejected — the yardstick must stay stable for seasons to be comparable; per-dispatch baselines drift with the menu. Kept parts: the reference is configurable to an exact pinned model when precision is wanted.
- **Cash-only savings** (kept-in-pocket = baseline − metered, subscription dispatches free): rejected — it implies subscription capacity is worthless and inflates savings with the subscription's sunk cost; the two-lens presentation states both truths instead.
- **Cash-primary tollbooth display**: rejected — breaks the visual comparability the price-asc ranking promises; the cash reality rides as an annotation instead.

## Consequences

- Ledger schema change is additive (`notional_usd`); `cost_usd`'s meaning narrows to metered cash; legacy lines reinterpret without migration (notional defaults to the old value, metered to $0 for subscription/local tiers).
- `Ledger.harvest()` gains `notional_spent_usd` and `metered_spent_usd` (with `spent_usd`/`saved_usd` retained as the notional-lens aliases for continuity); `format_harvest` renders the two-lens season summary with cash out labeled.
- Tollbooth `RouteOption` gains a cost-kind annotation (subscription | metered | local) alongside the existing `estimated_cost_usd`; ranking math is untouched.
- The benchmark harness (ticket #33, now unblocked) inherits its dollar definitions from these lenses: accuracy vs metered cash out and vs notional value, both already computed by the harvest.
- Terms canonized in CONTEXT.md: **Metered cost**, **Notional cost**, **Reference price**.

## Amendment (2026-08-25): cache-aware accounting

Dual-track accounting extends to provider prompt caching without redefinition. Ledger entries on api dispatches carry canonical `cache_read_tokens` / `cache_write_tokens` / `cache_ttl` extras (dialect-normalized at the backends; writes priced TTL-aware at 1.25×/2×). **Notional on API dispatches remains equal to metered** — cache discounts flow into both; cache savings are a separately computed third line (kept-via-cache = the full-price-minus-discounted input cost over cache-bearing dispatches), so kept-in-pocket (routing), cash out (metered), and kept-via-cache (caching) stay orthogonal and seasons stay comparable. The harvest renders a cache section (kept-via-cache, hit rate, reads-per-write, TTL cohorts, dispatch count) in text and JSON. **The cash-never-ranks rule extends by name**: cache-effective pricing is cash — observability only, never a route-menu input; reranking on cache economics requires a fresh ADR.
