# Key management: env → keychain → credentials file, presence probe at menu build, no key-entry CLI

Provider API keys resolve from three sources with fixed precedence: conventional environment variables first (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY` — explicit session override, container/CI-friendly), the **OS keychain first-class in v1** (macOS Keychain via `security`, service `kultivait`, account = provider name; Linux/Windows keychain backends follow platform support), then `~/.kultivait/credentials.toml` (0600, one key per provider section) as the plain-file fallback. Keys never live in `config.toml` (it round-trips `detect()`/`save_config` and may be shared for debugging); `keys.py` remains what it is — the tollbooth's TTY key reader, unrelated to provider credentials. **Route-menu candidacy requires a live presence probe at menu-build time**: a cheap authenticated GET per provider (Anthropic `GET /v1/models`, OpenAI `GET /v1/models`, OpenRouter `GET /api/v1/key`), issued concurrently with a short fail-fast timeout; a target whose probe fails drops from the menu exactly as a missing CLI binary would — the menu may shrink accordingly (docs/adr/0006-mixed-route-menu.md's shrink semantics), and offline machines degrade to local-only menus. Backend construction and serving keep #27's rule unchanged (key resolvable in the hierarchy at construction — no network); fat-margin dispatches never probe, and dispatch-time key failures belong to the retry-policy ticket's domain (#35). There is **no key-entry CLI and no validation UX**: keys enter via the user's shell, OS-native keychain tooling (`security add-generic-password`), or hand-editing the credentials file — all documented with copy-ready examples; no `last_validated` state is stored anywhere, and the menu-build probe's result is ephemeral, recorded only as menu metadata (which targets were probe-dropped). Key material never appears in logs, the ledger, or menu surfaces — menus name targets, not keys.

## Considered Options

- **OS keychain deferred to a later effort** (env + file only in v1): rejected — the keychain is the security-correct persistent home for long-lived credentials on the machines kultivait runs on; shipping it first-class avoids ever normalizing plaintext keys as the default store.
- **A `kultivait keys` subcommand** (add/list/remove/validate with masked display and entry-time validation): rejected — key entry and validation are not worth a new CLI surface; OS-native tooling and a documented file cover entry, and the presence probe covers freshness better than a stored stamp. Kept parts: the masking invariant survives as "never display key material anywhere" (nothing to mask without a display surface).
- **Construction-time resolvability as the candidacy gate** (offline menu builds, no network at menu time): rejected — menus would offer targets whose keys are stale or revoked; the probe guarantees every offered option is demonstrably working at the moment of choice, the strongest reading of ADR 0003's installed-only constraint. Its price — network latency per contested menu and offline degradation to local-only — is consciously accepted.
- **Live startup probe** (validate all providers at serve start): rejected — couples serve startup to provider availability and reads a provider outage as a missing key; the menu-build probe checks at the moment the answer matters.
- **Entry-time validation with persisted `last_validated_at`**: rejected — stored validation state goes stale and misleads; the probe is always-current by construction.

## Consequences

- Serving semantics split: construction (and fat-margin dispatch) requires hierarchy resolvability only; route-menu candidacy additionally requires a successful presence probe at menu build. A stale key therefore still serves non-toll frontier dispatches but never appears on a menu until it probes clean.
- Toll UX gains a bounded network dependency: probes run concurrently with fail-fast timeouts; their outcome (offered/dropped per target) rides the toll metadata for observability.
- Onboarding documentation (README section) carries the three-source contract with copy-ready env lines, a `security add-generic-password` invocation, and a credentials.toml snippet — this is the entire onboarding surface for v1; the setup TUI is untouched.
- Terms canonized in CONTEXT.md: **Presence probe**.
