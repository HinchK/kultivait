# Preprocessor treatment of tool-bearing requests: unconditional on contested, unchanged surface, sub-task candidates suppressed

The landed contract stands: every contested request runs the preprocessor regardless of tool-bearing-ness or which targets are registered (src/kultivait/server.py contested path; Map #4 decision #10) — no capability-gated skip is introduced even on machines where no tool-capable frontier exists and the analyze pass cannot change the dispatch outcome; the uniform code path is preferred and its latency on such machines is consciously accepted. The preprocessor's prompt surface is deliberately unchanged: the judge reads the last user message only (extraction never sees tool schemas, preserving the 4B tier's ≤8s p50 budget), receives **no tool digest**, and its targets enum stays **CLI-only** — no API targets are fitted, no fit-scale anchoring revision rides along. The verdict thresholds **[0.65, 0.85) are finalized as-is for all traffic** (tool and non-tool): #14's held-out validation is accepted as sufficient, its fit-clustering caveat (fits clustering ≥ 0.85, thinning the contested band) is consciously absorbed, and no further threshold validation is charted. The one behavior change: **sub-task candidates are suppressed on tool-bearing requests** — the preprocessor emits an empty candidate list when the request carries tools (agent harnesses plan their own work; the in-band channel stays reserved for compound non-tool prompts).

## Considered Options

- **Capability-gated preprocessing** (skip the analyze pass for tool requests when no tool-capable frontier is registered, since the dispatch is local regardless): rejected — the uniform contested-path rule keeps one code path; ~7s of latency on keyless machines is accepted as its price.
- **Tool digest + grown targets enum** (compact tool-name summary in the prompt; judge fits api-kind targets; fold in the fit-scale anchoring fix): rejected — the preprocessor surface does not move for tool traffic; mixed-menu ranking works without API fits (see Consequences). The calibration caveat is thereby closed by decision, not by revision.
- **Keep [0.65, 0.85) provisional + mandatory build-time tool-traffic eval** (mirror #14's methodology): rejected — thresholds are finalized now; the residual risk of a thin contested band on tool traffic is consciously accepted rather than re-validated.
- **Keep sub-task emission on tool traffic (capped)**: rejected — agent harnesses already plan; emitting candidates into their loops buys nothing and the harvest's candidate count goes quiet on tool traffic by choice. Kept parts: the in-band `kultivait_meta` channel and ledger fields survive unchanged for compound non-tool prompts.

## Consequences

- The preprocessor module itself needs no change for tool traffic; the one new rule is server-side: when the request bears tools, emitted `subtask_candidates` are emptied before recording/in-band return (preprocessor internals stay tool-blind).
- Mixed route menus (docs/adr/0006-mixed-route-menu.md) operate without API fits: API options carry fit 0.0 and rank through the total order's tail keys — on tool-bearing menus the capability filter has already removed CLIs, so API options order by notional price then id; on non-tool menus CLI options (fitted) rank by fit first and API options fill remaining slots by price. Coherent under ADR 0003's order; a future effort may re-open judge fitting of API targets.
- CONTEXT.md's **Sub-task candidates** entry is corrected: emission is for compound non-tool prompts; tool-bearing requests emit none.
- The map's fog items "Judge-prompt fit calibration" and "Subtask-candidate emission on tool-bearing traffic" both resolve here — the first by finalizing thresholds without revision, the second by suppression.
