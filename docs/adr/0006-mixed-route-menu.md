# Mixed route menu: capability filter over one grown candidate pool, local-first auto-policy, escalations archive unserved worthiness

When pay-per-token frontier providers (docs/adr/0004-api-frontier-surface.md) join installed CLI CLIs as serving targets, the route menu keeps ADR 0003's total order unchanged — judge fit descending → task_type capability match → notional price ascending → target-id — but grows its candidate pool to all registered, served targets of both kinds, with #28's uniform notional prices feeding the price comparison (cash stays an annotation and never ranks; docs/adr/0005-cost-model-duality.md). The one new rule is the **capability filter**: route-menu candidacy requires the target to be able to execute the request as sent — a tool-bearing request filters out CLI targets (which cannot accept client tools) leaving the tool-capable API targets plus the keep-it-local anchor (the local runtime serves tools), and the menu may legitimately shrink below three options rather than pad itself with unexecutable choices. When the filter empties the frontier side entirely (no API target registered) and local can serve tools, no trolltoll fires at all — the request dispatches straight through the normal local path. Auto-policy stays **local-first, capability-aware**: headless contested tool-bearing requests go local whenever the local tier can serve them as sent, take the top-ranked capability-filtered API target only when local cannot, and fail fast with an explicit error when no tool-capable target exists — never a silent local dump of a request local cannot execute. The escalation store sharpens to archive **unserved worthiness**: a tool request served by an API target is a normal dispatch with no archive; a frontier-worthy tool request served local because no tool-capable frontier existed archives as the downgrade (today's `tools_unsupported` behavior survives as the training signal); toll-path local choices archive under `route_choice`, never `fallback_reason` (ADR 0003).

## Considered Options

- **Kind-preferring tiebreak** (API-first for exact fits, or CLI-first for $0 cash, inserted before price/id): rejected — it structurally privileges one kind and lets cash influence ranking by proxy; #28 settled cash as an annotation on options, not an input to their order.
- **Offer CLI targets on tool-bearing menus with a "cannot take tools" badge**: rejected — violates ADR 0003's installed-only spirit (options must be executable, not advisory) and creates broken menu choices a human can select by mistake.
- **Hold a one-option confirmation toll when the menu reduces to local-only**: rejected — a 60s hold to confirm a decision with no alternative taxes headless agents and presence-less sessions for nothing.
- **Frontier-first auto-policy for tool agents** (tool loops are the expensive case local fumbles, per dogfooding insight C.1): rejected — abandons the reduce-first ethos on exactly the requests that are most costly; the capability-aware local-first rule already routes to API where local genuinely cannot serve.
- **Cheapest-capable auto-policy** (price-asc winner rather than fit-desc top): rejected — re-orders ADR 0003's auto-policy ranking rule mid-flight; price already sits third in the total order.
- **Archive every cloud-worthy prompt regardless of serving**, or **retire the tool-bearing archive once API targets exist**: rejected — the first dilutes the store until "escalation" stops meaning "underserved"; the second loses the signal on machines with no API keys and breaks the distillation loop.

## Consequences

- `build_route_menu`'s candidate pool becomes registered CLI targets ∪ registered-and-served api-kind tiers; its `prices` input unifies on notional per-target prices; the terminal tiebreak compares target ids across both kinds (stable, kind-blind).
- A tool-bearing request carries the capability filter: CLI candidates drop, api candidates and the local anchor remain; menus may render 1–4 options.
- `resolve_auto_policy` keeps its signature rule (local-first gated by serving capability, else top-ranked frontier of the filtered menu) and gains the fail-fast branch when no capable target exists.
- `escalations.save` fires for: downgrade serves (no capable frontier, `fallback_reason` set) and toll-path archives (`route_choice`); an API-served tool dispatch records no escalation.
- The preprocessor's treatment of tool-bearing requests (whether they are analyzed at all) remains ticket #30's question; this ADR defines the menu and dispatch semantics that hold either way.
- Term canonized in CONTEXT.md: **Capability filter**.
